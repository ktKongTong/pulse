# PulseBar App 侧界面与操作重构方案

## 1. 背景与问题定义

PulseBar app 侧当前已经不只是一个菜单栏状态展示工具。它同时承担本机应用监控、媒体状态读取、Live Listen 音频采集、endpoint 同步、SQLite 本地队列、Web 请求响应、授权状态提示和诊断观测等能力。这些能力本身是成立的，但它们在界面上没有被组织成清晰的用户任务，而是按照工程模块和调试需要堆叠到菜单栏、Dashboard、Settings、Sync、Live Listen 等多个入口中。

当前界面的主要断裂在于：用户看到的是系统内部状态，而不是自己下一步该做什么。比如 endpoint、server probe、SQLite queue、publisher、chunk、replay、permission、capture 等概念混在同一层级；开始监控、暂停监控、允许串流、停止采集、重连 server、Replay Endpoint 等操作也没有形成统一的运行模型。菜单栏与主窗口之间既重复展示状态，又没有明确区分“快速控制”和“完整管理”的职责。

这类问题不能通过局部改文案或移动几个按钮解决。根因是 app 侧缺少一套面向用户任务的信息架构和操作模型。继续在现有结构上追加功能，会让主界面越来越像调试面板，并且让每个新能力都暴露更多内部实现。重构必须从“用户如何完成配置、运行、监听和恢复”出发，重新定义入口、页面职责、状态表达和操作边界。

## 2. 重构目标

App 侧重构的第一目标是建立清晰的用户主路径：首次启动时完成必要授权和 endpoint 配置；日常使用时确认监控正在运行；Web 侧产生 Live Listen 需求时能够理解当前是否正在监听、由谁触发、为什么停止；出现错误时能够看到明确原因和下一步恢复动作。用户不应该先理解系统内部模块，才能完成这些基本任务。

产品层面的目标是把 PulseBar app 从“工程状态集合”收敛为“本机运行控制台”。主界面只展示用户判断运行是否正常所需的信息：当前监控状态、当前应用/媒体、同步健康、Live Listen 是否可用、是否需要处理错误。内部诊断信息仍然保留，但默认不进入主路径；只有在排查问题、开发调试或用户主动展开时才显示。

技术层面的目标是重构界面和操作编排，而不是打破现有 native 与 realtime 边界。`macosApp` 继续负责 SwiftUI 壳、设置和本机状态展示；本地运行态持久化继续以 Room / SQLite 为事实来源；realtime 聚合与统计继续归 Worker 和协议层负责。app 侧不应该绕过协议包自定义 wire shape，也不应该把 Worker 内部实现细节变成 UI 主概念。

重构后的验收方向如下：

- 用户能在一个连续流程里完成首次配置，而不是在多个页面之间猜测顺序。
- 日常菜单栏只承担轻量状态和少量高频操作，不再承载完整诊断面板。
- 主窗口按照任务组织，而不是按照工程模块堆叠。
- 错误状态必须给出可执行恢复动作，例如授权、配置 endpoint、重试连接或查看诊断。
- 工程诊断数据保留，但从默认界面降级到二级区域。

详见 [refactor-problems-and-architecture.md](./refactor-problems-and-architecture.md)。

## 4. 新信息架构

- 待重新讨论。
- 首先确立两个主体：`menubar` 与 `dashboard`。
- 后续从底层讨论什么情况下使用 `menubar`，什么情况下使用 `dashboard`。

## 5. 核心用户流程

- 首次启动与授权
- 配置 endpoint
- 开始监控
- Web 请求触发 Live Listen
- 错误恢复与重试

## 6. 界面重构方向

- Dashboard 重构
- `Overview` 页面移除
- Dashboard sidebar 顶部移除，直接从 nav 开始；底部只展示 media
- Dashboard 当前导航仅包含 `Connection / Reporting / Settings`
- Analytics 页面仅作为未来需求保留文档，不进入当前 dashboard
- Sync 重构
- Settings 重构
- 菜单栏重构

## 7. 操作与状态模型

- 运行态状态机
- 用户可执行操作
- 禁用态、错误态、恢复态规则
- 内部诊断信息的隔离策略

## 8. 实施分阶段

- Phase 1：文档与交互模型
- Phase 2：结构重排
- Phase 3：关键流程重做
- Phase 4：诊断面收敛
- Phase 5：视觉与可用性 polish

## 9. 验收标准

- 首次使用是否可完成配置
- 正常运行是否只看关键状态
- 错误时是否知道下一步
- 工程调试信息是否不再污染主界面
